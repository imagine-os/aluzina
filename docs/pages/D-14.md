## Purpose

The design system as data (P-07). Every colour in both themes with its CSS variable and its contrast ratio, the typography families and the rem ladder, spacing, radii, the responsive `--scale` bands with a live preview, and the target size and focus ring. It reads `src/design/tokens.ts` directly — the same file `npm run tokens` generates `tokens.css` from — so the page cannot drift from the stylesheet.

## Logic

- Variable names are derived with the same `camelCase -> kebab-case` rule as `apps/hub/scripts/gen-tokens.mjs`, so `surfaceRaised` reads `--color-surface-raised`.
- Contrast is the WCAG 2.1 ratio computed from the two hex values (sRGB relative luminance). `>= 4.5:1` passes, `3:1 – 4.5:1` is marked "Large text only", below 3 fails.
- The search filters every section by token name and variable name; sections with no match disappear and an `EmptyState` shows when nothing matches.
- "Preview band" recomputes the rem ladder, spacing and target in px for that band. With nothing selected it follows the real viewport and updates on resize.
- "Copy variable" writes `var(--name)` and toasts; `qa.copyToken` accepts the token name (`color.accent`), the bare key (`accent`) or the variable (`--color-accent`).
- **Edit token is a `Placeholder`** (P-09): tokens are edited in `src/design/tokens.ts` and regenerated, and the running app has no write path to the repo. The action `qa.editToken` is registered and answers with the not-wired toast rather than silently doing nothing.

## Contrast findings (first run)

26 of the 28 pairs pass 4.5:1. Two do not, and both are real:

| Theme | Pair | Ratio | Verdict |
| --- | --- | --- | --- |
| light | `accent` on `surface` (#d97706 on #ffffff) | 3.19:1 | large text only — fine for a 1.25rem+ heading or an icon, not for body copy or a 0.75rem badge label |
| dark | `accentText` on `accentSoft` (#141210 on #4a3a12) | 1.70:1 | fails — near-black text on a dark amber wash is unreadable |

The dark `accentText` / `accentSoft` pair is the one to fix: in light mode `accentSoft` is a pale wash (#fde68a, 14.04:1 with `accentText`), but the dark value inverted the wash without inverting its text colour. Anything that renders `accentText` on `accentSoft` — a soft accent chip or a highlighted row — is unreadable in dark mode. Proposed in the changelog as a decision for the integrator rather than changed here (tokens are outside this module's folder). Body pairs are healthy in both themes: `text` on `bg` / `surface` / `surfaceRaised` is 13.42:1 to 17.49:1, `textMuted` 5.40:1 to 7.98:1.

Nothing on this page hides a number behind colour alone: every verdict carries a word as well as a tone.

## Responsive and input check (P-01, P-03)

Verified with Playwright at 360 / 390 / 768 / 1280 / 1920 / 2560 / 3840: no page overflow at any width, no console errors, no missing-translation markers, root font 16 / 16 / 16 / 16 / 18 / 24 / 32 px. Zero sub-44 px controls on this page (the swatch chips are decorative `aria-hidden` spans, not controls). The swatch grid is `auto-fill minmax(20rem, 1fr)`, so it is one column on a phone and five on a 4K TV; the tables scroll inside `.table-wrap` rather than the page. Keyboard: the demo button in the last card is there to tab to and confirm the focus ring.

## Strings (P-13)

## Open questions

- Shadow tokens (`--shadow-sm / md / lg`) are requested: six elevations are hard-coded across Toast, Modal, Drawer, HubHeader and DevTools.
- Should the type ladder become real tokens (`tokens.fontSize`) instead of a documented convention? Today component CSS picks rem values by hand.
- A `Swatch` library component would remove the only bespoke visual on this page.
