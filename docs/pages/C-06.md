# C-06 - Strategic brief (client)

- route: `/#/client/brief`
- surface: client (PhoneShell)

## Purpose

The strategic brief of the playbook (service 01, phase 2: USER / SPACE / AESTHETIC DIRECTION / EXPECTATION) as a form the client fills in their own time. The answers are saved on their engagement, so the studio reads them before the session instead of chasing them over chat.

## Layout (top to bottom)

1. `PageHeader` (C-06) whose subtitle is the answered count ("1 of 23 answered").
2. Project `Select` when the client has more than one project.
3. One `Card` per playbook group (User, Space, Aesthetic direction, Expectation) with a `Textarea` per question.
4. The "Save the brief" primary button, with a "Brief saved." toast.

## Data

Reads `projects` (scoped), `engagements`. Writes `engagements.brief`.

## Rules

Service 01 phase 2 of the playbook; `OPERATIONAL_ASSETS` maps "brief forms" to `engagements.brief`.

## Logic

- The questions are read from `SERVICES` code `01`, phase `01-2` (grouped items), so the form *is* the playbook: change the playbook and the form changes.
- Answers are keyed `checkKey('01-2', index)` over `phaseItems()` — the same key scheme the checklists use. Keys the studio wrote under other names (the seeded `client.goals`, `user.profile`, …) are merged on save, never dropped.
- Save writes the whole `brief` object once, with `basedOn` the engagement the client was editing (D-024), then toasts. Verified: the answer survives a reload.
- Changing the project clears the local draft so two projects' answers cannot mix.
- A project without an engagement gets an `EmptyState` instead of a form that would write nowhere.

## Open questions

- The brief is guarded by `own.projects.read`; a dedicated `own.brief.write` permission would be honest (requested).
- Autosave on blur would suit a long form on a phone better than one Save button; today an unsaved draft is lost on navigation.
