## Layout (top to bottom)

1. `PageHeader` with a `Placeholder` "New check".
2. Three `StatTile`s: pending, with issues, passed.
3. One `Card` per check: title, "project - checked by", `StatusPill`; a `Checkbox` list of its items; the progress line; the notes `Textarea`; a row with the `Placeholder` "Add check item" and "Save notes".
4. Card footer: the pass rule as a hint (until every item is ticked) and the "Report issues" / "Mark passed" buttons.

## Data

Reads `consistencyChecks`, `projects`. Writes `consistencyChecks.items`, `.status`, `.notes` and `projects.approval`.

## Rules

- Approval chain (`roles-and-portals.md`): passing writes the check to `passed` **and** the project to `awaiting-founder`; reporting issues writes `issues` and returns the project to `in-check`.
- "Mark passed" is disabled until every item is ticked, so a half-checked proposal cannot reach the founder.
- Everything on this page needs `projects.check`; without it the checkboxes and notes are disabled and the buttons are not rendered.

## Logic

- Ticking an item rewrites the whole `items` array by index (the schema stores it as an embedded list) and the card re-renders from the live table.
- Notes are edited locally and written only on save, so a half-typed note never reaches the founder; the save button is disabled while the text equals the stored value, and a change made elsewhere re-syncs the field.
