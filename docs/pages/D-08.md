# D-08 - Demo simulator

- route: `/#/dev/simulator`
- surface: dev
- status: built
- spec: `apps/hub/src/modules/tools/specs.ts` (`simulatorSpec`)
- model: Opus 5

## Purpose

The app running in a phone frame and a desktop frame side by side, as any demo role, in either language and theme. It is how a journey gets shown to Justin or a client from one screen — the "demo simulator (mobile + desktop)" the Hub deliverable asks for (P-12) — without a second device and without leaving the dev tools.

## Layout (top to bottom)

1. DesktopShell (dev surface).
2. `PageHeader`: breadcrumb, h1, subtitle.
3. Controls: route `Select` (every route with a menu entry plus the public ones and the hub, labelled `code · name (#path)`, ordered by surface), role `Select` (the demo users), language `Select`, theme `Select`, and a "Sync frames" `ToggleButton` with its hint.
4. Presets row: Client phone journey, Founder dashboard, Ops schedule, Public services.
5. The shared-origin note.
6. Two device frames, side by side from 1024 px and stacked below it: **Phone** 390 × 844 and **Desktop** 1280 × 800, each with its size caption, an "Open in new tab" `Button` and the `<iframe>`.

## Data

None. Routes come from `RoutesContext`, roles from `src/auth/demoUsers`, language and theme from the app providers.

## Rules

D-015: the frames are the real app behind the real guards; `?as=<role>` only picks the demo identity.

## Logic

- Each frame is an `<iframe>` of `./index.html?as=<role>#<path>` — the app is a HashRouter, so one iframe per frame — with a translated `title` and `loading="lazy"`.
- The desktop frame is rendered at its real 1280 × 800 and `transform: scale()`d to its column; the phone at 390 × 844 and scaled only when the column is narrower (which is what happens at 360). Both scales come from a `ResizeObserver` on the column, and the caption says the percentage.
- Language and theme go through the app's providers, which own `aluzina.lang` / `aluzina.theme`; the frames are then remounted (a key bump) so they load with the new value.
- **Same origin, shared storage**: the frames share this tab's `localStorage` and `sessionStorage`. So the parent's language and theme follow the simulator, the `?as=` role of the last loaded frame becomes this tab's user on the next reload of this tab, and each frame shows up in the presence bar as its demo user (D-023). The page says so in a note; it is a property of the demo, not a bug.
- Sync on: the route Select drives both frames. Sync off: it drives the phone only, and the desktop stays wherever it was browsed inside the frame.
- A preset sets route and role together and turns sync on; a preset whose route is not registered yet is a `Placeholder` (P-09) — in this pass that is whatever the client and public modules have not landed.
- The simulator's own route is left out of the route Select so a frame cannot nest the simulator in the simulator.

## Actions (P-05)

| id | label | intent | permission | params |
| --- | --- | --- | --- | --- |
| `tools.simulateRoute` | Simulate a route | show {route} in the simulator | `dev.tools` | `route: string` |
| `tools.simulateRole` | Simulate a role | view the simulator as {role} | `dev.tools` | `role: enum:founder\|ops\|studio\|brand\|marketing\|client\|dev` |
| `tools.simulateLang` | Simulate a language | switch the simulator to {lang} | `dev.tools` | `lang: enum:en\|es` |
| `tools.simulateTheme` | Simulate a theme | switch the simulator to the {theme} theme | `dev.tools` | `theme: enum:light\|dark` |
| `tools.openSimulatedTab` | Open a frame in a new tab | open the {frame} frame in a new tab | `dev.tools` | `frame: enum:phone\|desktop` |
| `tools.toggleFrameSync` | Toggle frame sync | make both frames follow the same route | `dev.tools` | `on: boolean` |
| `tools.applyDemoPreset` | Apply a demo preset | set up the {preset} demo | `dev.tools` | `preset: enum:clientJourney\|founderDashboard\|opsSchedule\|publicServices` |

All seven register while the page is mounted.

## Components

`PageHeader`, `Select`, `ToggleButton`, `Button`, `Placeholder`, `EmptyState`. The device frame itself is the one piece built in the page (see "Open questions").

## Real vs mock / placeholder

Real: both frames run the real app, the role / language / theme / route controls, "Open in new tab", the sync toggle and the presets whose route exists. Placeholder: a preset whose route is not registered yet.

## Responsive and input check (P-01, P-03)

Verified at 360, 390, 768, 1280 and 1920 (`spec.checkedAt`), plus a 2560 overflow check: no horizontal page scroll at any width. The frames stack under 1024 px and both scale to their column, so nothing is ever cut off. Every control is a labelled 44 px target in a single Tab order; the iframes are one Tab stop each and carry a translated title; nothing is hover-only or drag-only.

## Strings (P-13)

Namespace `tools.sim.*` + `core.*`. EN complete, ES complete.

## Open questions

- A `DeviceFrame` component (real size + scale-to-column + caption + open-in-tab) belongs in the library; a tablet frame (768 × 1024) and a TV frame (1920 / 3840, for the 10-foot check) are the obvious next two.
- The frames cannot be driven without a reload because they share storage instead of a message channel; a small `postMessage` protocol in the app would let the simulator change route, language, theme and role live, and would also be the seam for scripted demos.
- Should the simulator be able to record a journey (a list of route + role steps it walks) for a client presentation?
