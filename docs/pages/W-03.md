# W-03 - New project from template

- route: `/#/founder/work/new`, `/#/ops/work/new`
- surface: founder | ops (same page, the portal's shell)
- status: built
- spec: `apps/hub/src/modules/work/specs.ts` (`newProjectSpec(surface)`)
- model: Fable 5.1 (design), Opus 5 (implementation)

## Purpose

The founder starts every project by duplicating a 349-task Asana project by hand, once per language, which is why 2023 residue keeps leaking into 2026 work (`docs/knowledge/asana-conventions.md`). This page does it properly: choose the template, name the project and its client, keep the phases that apply, pick the spaces, and the OS writes the sections and the whole task tree with owners and deliverables, then opens it in W-02. Justin, prompt 0017: "assigning tasks for new projects and things like that, as well as lincoln tasks to deliverables, who's working on them".

## Layout (top to bottom)

1. `PageHeader` (W-03) with the breadcrumb portal / Work / New project and an "All work" button.
2. `Tabs`: the five steps, `1. Template … 5. Review`, arrow-key navigable.
3. One `Card` per step:
   - **Template**: `Select` of the templates (one today), the template's source sentence and a `KeyValue` of its counts (phases, template tasks, repeated per zone, deliverables).
   - **Project**: project name, client (`clients` rows), project type, lead designer (role), service (playbook `SERVICES`).
   - **Phases**: one `Checkbox` per phase with "n tasks · owner <role>", all on by default.
   - **Zones**: `Checkbox` per `ZONES` entry plus an "Add a zone" form, and the resulting task count.
   - **Review**: four `StatTile`s (sections, tasks, zones, deliverables) and a `KeyValue` of every choice, with a `Badge tone="warning"` where something is missing.
4. Back / Next, and "Create the project" on the last step.

## Data

Reads `clients` and (through the template) the `deliverables` catalog. Writes `projects` (one row), `sections` (one per chosen phase) and `tasks` (the whole tree, parents first). The template itself is **not** data in the database: it is typed data in `apps/hub/src/domain/templates/` (D-062).

## Rules

None numbered. Permission `projects.write` (founder always; operations since this pass, D-062): the route is guarded and Create is disabled without it, while the action still answers readably (D-047).

## Logic

- `tpl-aluzina-workflow` is the merge of the founder's two Asana template projects plus PROYECTO HOY's kickoff section; `en` labels without an Asana source are the integrator's translations (D-004).
- `templateCounts(template, phaseIds, zoneCount)` is what the review step shows; nothing is written until Create.
- `expandTemplate()` returns the rows with `parentKey` instead of ids and parents before children; a `zoneScoped` subtree is cloned once per chosen zone with the zone name appended to its root title (`13. 1 MODELADO DE CADA ESPACIO — Cocina`), so eleven zones cost 279 tasks instead of storing eleven copies in the template.
- Each task is assigned to the team member of its `ownerRole` (founder -> Alejandra, studio -> Sarai, ops -> Miguel, brand -> Angélica) and keeps `templateTaskId` so a later template change can be diffed against a live project.
- The new project starts `pipelineStatus: briefing`, `phase: concept`, `approval: draft`, `creativeDirection: pending`, `budgetCop: 0`, no due date; the summary records the template, the zone count and what is still missing.
- Step state is component state (nothing persisted): the page is a one-shot form, not a saved draft.

## Actions (P-05)

| id | label | intent | permission | params |
| --- | --- | --- | --- | --- |
| `work.selectTemplate` | Choose the template | use the project template {template} | `projects.write` | `template: id` |
| `work.setTemplateStep` | Go to a step | go to the {step} step | `projects.write` | `step: enum:template\|project\|phases\|zones\|review` |
| `work.setProjectName` | Name the project | call the new project {name} | `projects.write` | `name: string` |
| `work.selectClient` | Choose the client | the new project is for the client {client} | `projects.write` | `client: id` |
| `work.selectTemplatePhases` | Choose the phases | include the phases {phases} | `projects.write` | `phases: string` |
| `work.selectTemplateZones` | Choose the zones | include the zones {zones} | `projects.write` | `zones: string` |
| `work.addZone` | Add a zone | add the zone {zone} to this project | `projects.write` | `zone: string` |
| `work.createProjectFromTemplate` | Create the project | create the project from the template | `projects.write` | – |

All eight are registered while mounted, so the whole flow runs from `window.__aluzina.actions` (verified: name, client, two phases, two zones plus a custom one, review, create -> 2 sections and 70 tasks).

## Real vs mock / placeholder

Everything writes real rows through the DataProvider. No `Placeholder`. Not built: editing a template in the product, a second template, saving a draft of the form, setting budget / dates here (they belong to the project).

## Responsive and input check (P-01, P-03)

`checkedAt` 360 / 390 / 768 / 1280 / 1920 / 2560. Smoke at 390 and 1280 on both surfaces: no console errors, `scrollWidth === clientWidth`. The step tabs scroll horizontally under 768 px; the field grid and the zone list are `auto-fit` so they collapse to one column on a phone; the stat tiles wrap. Keyboard-only run: 60 tab stops from the skip link through the tabs and every field, each with the 3 px focus ring; every control is a library control >= 44 px; nothing hover-only or drag-only.

## Strings (P-13)

`work.new.*` (module). EN complete, ES complete. The template's own labels are `{ en, es }` in `domain/templates/aluzina-workflow.ts` and render with `pick(text, lang)`, so the created tasks are written in the language the person is using.
