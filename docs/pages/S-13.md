## Purpose

One archived project as a portal: the example Justin asked for with JOE GALLINA INTERIOR. Everything the studio produced for that project is on one page, in the order it was produced, previewable without leaving the system — "each of the items and deliverables need to be previewable from inside the system", "build a pipeline and organize the documents in order". The page also answers the other half of the ask, "sets of related examples to show specific clients", with a Related block that finds the projects sharing tags with this one.

## Layout (top to bottom)

1. `PageHeader`: breadcrumb Studio portal / Archive / project, title, subtitle "N files across M stages of the delivery order".
2. **Hero**: cover `Thumb` (16:9, lg) beside name, client, year, location, project type, `StatusPill`, lifecycle `Badge`, and, for `archive.curate`, a **Tags** row with the `TagEditor` and its Save / Undo buttons (read-only `Badge`s for everyone else), plus the buttons **Open in Dropbox** (external, `sourceFolderUrl`), **Open in Work** (`/<surface>/work/:projectId`), **Open space** (when a `spaces` row has `aboutId` = the project) and **Add to portfolio set**.
3. **Delivery order**: a horizontal rail built from `DELIVERY_STAGES` in `order`, sub-headed by `pipelineGroup` (Design, Sale, Build, Close — in delivery order, so design comes before sale). Each stage is a >= 44 px button with its glyph, label and file count; a stage with no files reads "no files" in muted text and is still shown, because the empty stages are part of the map.
4. **Files** toolbar: `SearchField`, `Select` stage, `Select` file type, Grid | List `ToggleButton`s, **By stage | By folder** `ToggleButton`s, and — for `archive.curate` — the line "Open a file to edit its tags, its stage and the project cover." (tagging moved into the drawer in ar-09; the old `Placeholder` "Tag file" is gone).
5. **Files**, either one section per stage that holds files (in delivery order, folders inside each stage) or, in "By folder" mode, the studio's own numbered folder tree. Each file is one button holding a `Thumb` (thumbnail or type icon, badge = "N p." for a PDF with a page count, else the extension, caption = the file name).
6. **Preview `Drawer`**: file name as the title, a meta line (type, size, modified, stage `Badge`, folder), the `DocumentViewer`, then Download, Open at source, Copy link, Previous file, Next file and "i of n", and for `archive.curate` a **Tags and stage** block: the `TagEditor` (chips + suggestion combobox) with **Save tags** / **Undo changes**, the **Delivery stage** `Select`, and **Set as cover** (or the `Badge` "Project cover" when it already is one, or a `Placeholder` when the file has no render yet).
7. **Related**: the client card, the Spaces post about the project, and up to six "Related examples" cards for projects sharing at least two tags.

## Data

Reads `projects` (the project and the tag-sharing candidates), `assets` (`kind: 'file'`), `relations` (`belongs-to` for this project's files, `for-client` for the client), `clients`, `spaces` (`aboutType: 'projects'`, `aboutId`), `filings` and `posts` (the Spaces post about the project). Writes (ar-09): `assets.tags` and `assets.stage` and `projects.tags` / `projects.coverAssetId`, all behind `archive.curate` (studio, brand, founder; changelog 0021) and all through `data.update(entity, id, patch, { basedOn: row.updated_at })`, plus `localStorage['aluzina.archive.set']` for the portfolio set.

## Logic

- **Stage of a file** is `asset.stage`, set at seed time by `stageFor(folderPath, name)`; a file with no stage falls into `other`, so nothing disappears.
- **Two groupings**, in `?group=stage|folder`. By stage: one section per stage that has files, in `DELIVERY_STAGES` order, folders inside sorted with `compareFolderPaths`. By folder: the whole tree in the studio's own numbering, sorted with `folderOrderKey`, each heading a breadcrumb of `folderLabel` segments with the number kept as a small muted prefix ("Diseño > 03 Planos"). Folders that hold no files of their own — an ancestor such as `DISEÑO`, or a numbered folder the studio created and never filled — still render, muted, with "empty folder", so the structure is complete. That is the "documents in order" view.
- **The rail filters and scrolls**: clicking a stage sets `?stage=` and scrolls its section into view; clicking the same stage again clears the filter. Arrow keys (and Home / End) move along the rail; every stage button keeps a normal tab stop, so a keyboard person can also just tab.
- **The preview is URL state** (`?file=<assetId>&page=N`), so a specific file in a specific project is a link. Previous / Next walk the *currently filtered* list, wrapping, and "i of n" says where you are. `page` drives the `DocumentViewer`, which renders the paged image viewer when the asset has `previewUrls`, a PDF object/iframe chain when it has a served `url`, a big image or a `<video>` for those families, and otherwise its own sentence plus the file-type icon — never a blank frame. Escape closes the drawer.
- **Related** is three reverse queries: the client from a `for-client` relation (falling back to a name match while the seed has no relation), the Spaces post through the project's space and its `filings`, and the projects that share two or more tags, ranked by shared-tag count then year, capped at six.
- **Tags are real writes** (ar-09). The `TagEditor` holds a draft; **Save tags** writes the whole array once (`data.update('assets', id, { tags }, { basedOn: asset.updated_at })`, or `projects` for the project's own tags), so one save is one row version and the D-024 conflict toast (`core.data.conflict`, from `DataContext`) names whoever was overwritten. **Undo changes** drops the draft without writing.
- **Tags are free text**, trimmed, lower-cased, de-duplicated, `#` stripped (`normalizeTag` / `parseTags` in the `TagEditor`), max 12 per row. The suggestion list is the live union of every tag on a file asset, the `tags` registry names and the `DELIVERY_STAGE_IDS`, so the vocabulary converges without a closed list and the `tags` registry can gain rows lazily later. A tag saved here shows up in S-12's Tag filter without a reload (D-023): verified in two tabs.
- **The delivery stage** is a `Select` over `DELIVERY_STAGES` that writes `assets.stage` immediately (no Save), because the rail, the sections and every count read the same row.
- **The cover** is `projects.coverAssetId`. "Set as cover" is offered only for an image or a PDF; a file with no `thumbnailUrl` gets a `Placeholder` saying the render does not exist yet (D-047 keeps the action registered), and a `confidencial` or redacted file is never offered as a cover at all (D-059) — the action itself also refuses it.
- **Without the permission** the editors are not rendered at all and the actions answer `'no permission: archive.curate is needed to tag a file'` (or `… to set the cover`), so the bus, voice and WebMCP hear the same truth as the UI. `archive.curate` (changelog 0021, D-067) is held by `studio`, `brand` and the founder; it replaced the ar-09 pass's `assets.manage` / `projects.write` checks, which had left the studio unable to tag its own archive.
- The `Drawer`'s `onClose` is now a `useCallback`: an unstable handler made `useFocusTrap` re-run on every render and steal focus back to the close button after each tag edit.

## Actions (P-05)

| --- | --- | --- | --- | --- |
| `archive.openFile` | Preview a file | preview the file {asset} | `projects.read` | asset: id |

| `archive.setStage` | Move a file to a stage | move the file {asset} to the delivery stage {stage} | `archive.curate` | asset: id, stage: string |
| `archive.setCover` | Set the project cover | use the file {asset} as the cover of this project | `archive.curate` | asset: id |
| `archive.setProjectTags` | Tag the project | tag the project {project} with {tags} | `archive.curate` | project: id, tags: string |
| `archive.addToSet` | Add this project to the set | add this project to the portfolio set | `projects.read` | — |

All nineteen register while the page is mounted, for every role: a person without the permission gets the refusal string instead of `not-live`. `tags` is accepted as an array or as a comma / semicolon string, `stage` must be a `DELIVERY_STAGES` id (otherwise `no such stage: <value>`). Handlers that take an `asset` accept an id or a file name and fall back to the open file; `archive.setProjectTags` refuses another project's id because the page is one project. Every handler returns something readable. Verified through `window.__aluzina.actions.run` as founder: `archive.tagFile {asset:'…03-layout', tags:'plano, PLANO , bus ar09'}` -> `'03 LAYOUT.pdf: plano, bus ar09'` (de-duplicated and lower-cased), `archive.setStage {stage:'nope'}` -> `'no such stage: nope'`, `archive.setCover` -> `'Joe Gallina Interior cover: 03 LAYOUT.pdf'`, `archive.setProjectTags {tags:['Archive','archive','bus']}` -> `'Joe Gallina Interior: archive, bus'`; as studio (ar-09 pass, before the permission existed): `'no permission: assets.manage is needed to tag a file'`; since changelog 0021 the refusal reads `'no permission: archive.curate is needed to …'` and studio holds it (re-verified as studio at 390 and 1280: the drawer's tag block renders and a saved tag persists).
