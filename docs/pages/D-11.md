# D-11 - Testing hub

- route: `/#/dev/testing`
- surface: dev
- status: built
- spec: `apps/hub/src/modules/qa/specs.ts` (`testingSpec`)
- model: Opus 5

## Purpose

The QA matrix the workspace policy asks for, in the product. One row per registered route, one column per matrix width (360 / 390 / 768 / 1280 / 1920 / 2560 / 3840), so anyone can see at a glance which pages have been checked where, what each spec still lacks, and open a page at a given width as the role that uses it. It also carries the P-08 explanation of in-product annotation and the "File a bug" control, which is a `Placeholder` until the `feedback` entity exists.

`docs/screenshots/D-11/en-390.jpg`, `en-1280.jpg` — not captured in this pass. Local Playwright captures at the seven matrix widths were reviewed.

## Layout (top to bottom)

1. DesktopShell (dev surface, `dev.tools`; nav group "Quality and testing").
2. `PageHeader`: breadcrumb, title, subtitle.
3. Four `StatTile`s: routes, fully checked (all seven widths recorded), average completeness, width cells checked (n of routes x 7).
4. `FilterBar`: `SearchField` (code, page, path, surface), surface `Select`, "Incomplete only" `Checkbox`, the "Load screenshot manifest" `Placeholder`, summary, Clear.
5. `DataTable`: code, page (name over path), one column per matrix width, EN/ES, spec score `Badge`, placeholders, screenshots. Sortable, rows focusable, collapses to stacked cards under 768.
6. A note under the table stating what the two dash columns mean.
7. Card "Feedback and bugs (P-08)": what annotation and agent triage are, why the store does not exist yet, and a `Placeholder` "File a bug" button.
8. `Drawer` (row activation): path / surface / score / recorded and missing widths, the missing spec checks, "Open at 390 / 1280 / 1920", and the simulator link.

None. Routes come from `RoutesContext`; scores come from `specCompleteness()` in `src/specs/PageSpec.ts`.

None.

## Logic

- A width cell is `✓` when the width appears in `spec.checkedAt` and `○` otherwise. **The matrix reports what builders recorded, not a live measurement** — the subtitle says so, because a tick that looks like a robot's verdict would be worse than no tick.
- Each tick carries an `aria-label` ("checked at 1280 px" / "not recorded at 1280 px"), so the glyph is never the only information.
- Spec score is `specCompleteness()` (9 checks); "Incomplete only" keeps the routes with at least one missing check. Average completeness uses `Math.floor`, so it never reads 100% while a page is incomplete.
- "Open at {width}" calls `window.open(pathname + '?as=' + role + '#' + path, name, 'width=...,height=...')` with a sensible device height per width (390 -> 844, 1280 -> 800, 1920 -> 1080). The role is the first `spec.roles` entry that is a real role id, else `roleForSurface(surface)`, else the current role. The browser may clamp the window size, and a blocked popup toasts. Routes whose path has a `:param` cannot be opened from here: the buttons are disabled and the drawer says why.
- The simulator button is a real link when a route for `/dev/simulator` (D-08) is registered and a `Placeholder` while it is not — the page checks the live route list rather than assuming.
- Placeholder counts per page and screenshot availability cannot be read from a running page (one needs a visit, the other needs `docs/screenshots/<CODE>/`), so both columns show a dash with a title, and the single "Load screenshot manifest" `Placeholder` above the table is the control that will do it.

## Components

`PageHeader`, `StatTile`, `FilterBar`, `SearchField`, `Select`, `Checkbox`, `DataTable`, `Badge`, `Button`, `Drawer`, `KeyValue`, `Card`, `Placeholder`.

## Real vs mock / placeholder

Real: the matrix, the scores, the filters, the stats and "Open at width" (it really opens a sized window as the right role). `Placeholder` (2 on the page, 1 more in the drawer when D-08 is absent): "Load screenshot manifest", "File a bug", and the simulator link. Nothing is mock data — every number is derived from the live route manifest.

## Responsive and input check (P-01, P-03)

Verified with Playwright at 360 / 390 / 768 / 1280 / 1920 / 2560 / 3840: `scrollWidth === clientWidth` on the document at every width, no console errors, no missing-translation markers. The matrix is a wide table by nature: from 768 to about 1500 px it scrolls **inside** `.table-wrap` (the shared `DataTable` scroll container) rather than pushing the page; under 768 it collapses to stacked cards where every cell shows its header. The only sub-44 px element is the native `input.check__box` of "Incomplete only" (24 px) whose `<label>` hit area is 44 px, as resolved in `docs/qa/0001-work-views-matrix.md`. Keyboard: filters, the placeholder controls, the sort headers and the rows are all in order; Enter opens the drawer, Escape closes it.

## Strings (P-13)

Namespace `qa.testing.*` + `core.*`. EN complete, ES complete. Spec-field names in the "missing checks" list (`purpose`, `layout`, `checkedAt`, ...) are rendered as `<code>` identifiers, not prose, and stay in English on purpose.

## Open questions

- The EN/ES column reads `✓ / —`: English is complete by construction (the `en` key is required by `StringEntry`) but per-page Spanish coverage is not measurable at runtime. It would become real if `strings` tables were attributed to pages, or if a build step diffed `en` and `es` keys per module.
- `.table-wrap` scrolls horizontally but is not focusable, so a keyboard-only user cannot scroll it without tabbing to a control inside. Requested as a `DataTable` change (`tabindex="0"` + `role="region"` + an accessible name when the table overflows).
- Should `specCompleteness` require the full seven-width matrix instead of three widths, now that the matrix is visible? That would drop the average sharply and honestly.
