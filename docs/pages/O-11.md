# O-11 - Change orders

- route: `/#/ops/change-orders`
- surface: ops
- status: built
- spec: `apps/hub/src/modules/ops/specs.ts` (`changeOrdersSpec`)
- model: Opus 5

## Purpose

Change control of service E (stage 8): every request made after the design is approved becomes a change order with its description, reason, extra cost, extra time and a decision, recorded **before** the work continues. Miguel writes them, Miguel or Alejandra decide them, and nothing unapproved can be marked executed.

## Layout (top to bottom)

1. `PageHeader` (O-11) with a "New change order" primary `Button` (only with `changeOrders.manage`) and the G-14 rule as a note under it.
2. Four `StatTile`s: waiting for a decision, executed, extra cost, extra days (the last two count approved and executed orders only).
3. `FilterBar`: project `Select`, status `Select`, count, Clear.
4. `DataTable`: project, description, extra cost, extra days, requested by, approved on, status `StatusPill`; row actions Approve / Reject (on `requested`) and Mark executed (on `approved`).
5. `Modal` "New change order": project, description, reason, extra cost, extra days.
6. `Drawer`: the order in full with a `G-14` `Badge` while it may not be executed, the decision buttons, and "Mark executed" — visible but disabled with the reason as its title when the order is not approved.

## Data

Reads `changeOrders` and `projects`. Writes `changeOrders.status` and `changeOrders.approvedAt`, and creates `changeOrders` rows.

## Rules

- **G-04** scope changes are documented before work continues (the order exists before anything is executed).
- **G-14** description, reason, extra cost, extra time and approval are all recorded, and an unapproved change is never executed.

## Logic

- Approve writes `status: 'approved'` and `approvedAt` = today; Reject writes `status: 'rejected'` and clears `approvedAt`; both need `changeOrders.manage`.
- G-14 is enforced in the write, not only in the UI: `execute()` re-reads the stored row, refuses anything that is not `approved` with a toast and returns the reason, so the rule holds whether the call comes from the button, another tab or `runAction`. The drawer button is additionally disabled with that reason as its `title`.
- A new order is always `requested`, with `requestedById` set to the person writing it.
- The totals ignore `requested` and `rejected` orders: a change that has not been approved has not changed the budget or the schedule.

## Actions (P-05)

| id | label | intent | permission | params |
| --- | --- | --- | --- | --- |
| `ops.newChangeOrder` | New change order | record a change order on {project} for {description} | `changeOrders.manage` | `project: id`, `description: string`, `reason: string`, `cost: number`, `days: number` |
| `ops.approveChangeOrder` | Approve change order | approve the change order {changeOrder} | `changeOrders.manage` | `changeOrder: id` |
| `ops.rejectChangeOrder` | Reject change order | reject the change order {changeOrder} | `changeOrders.manage` | `changeOrder: id` |
| `ops.executeChangeOrder` | Mark change order executed | mark the change order {changeOrder} as executed | `changeOrders.manage` | `changeOrder: id` |
| `ops.filterChangeOrdersProject` | Filter by project | show the change orders of {project} | `changeOrders.manage` | `project: id` |

All five register while mounted (verified: declared 5, none missing from the live list).

## Real vs mock / placeholder

Seed data: the two Noam orders.
