# M-02 - General commercial process

- route: `/#/manual/commercial`
- surface: manual
- status: built
- spec: `apps/hub/src/modules/manual/specs.ts` (`commercialSpec`)
- model: Opus 5

## Purpose

How a client becomes a project: the seven channels a lead can arrive through, everything registered immediately (the lead record and the commercial data, each field named with the `leads` column it becomes), the first pipeline status, the ten qualification questions to ask, and how the answers route to one of the five services under the commercial rule G-10. A "Route a client" widget lets anyone try the routing without touching the CRM.

## Layout (top to bottom)

1. `PageHeader` with breadcrumb Manual > Commercial process and **Print / PDF**.
2. Lead entry channels: the 7 `LEAD_CHANNELS` as badges.
3. Immediate registration: `KeyValue` of `LEAD_RECORD_FIELDS`, then of `COMMERCIAL_FIELDS`; each value is the `leads` column. Then the first status (`LEAD - NEW`) as a `StatusPill`.
4. Initial qualification: the 10 `QUALIFICATION_QUESTIONS` as an ordered list, closed answers shown as badges, each with its `qualification.<key>`.
5. Service routing: the commercial rule G-10 in a raised card, then the 5 services with their central question / promise and a link into each manual page.
6. Route a client: five `Select`s for the closed questions plus the on-site-visit question, and a result card with the suggested service, the follow-on service when there is one, the reason, **Clear answers**, a `Placeholder` **Create lead** and a link to the suggested service.

## Data

None written. Reads no entities: the fields shown are the schema's column names, the answers live in component state only.

## Rules

- **G-10** (commercial) is rendered from `GOVERNANCE_RULES`, not retyped: never sell a small service when the diagnosis shows the client needs a deeper scope.
- The routing is a suggestion (`leads.suggestedService`); the founder decides. The widget says so and cannot write.

## Logic

- `routeService(answers)` runs on every change; the result is `{ code, then?, reason }` straight from the domain module, so the manual and the intake flow can never disagree.
- Only closed questions become `Select`s; the open questions (what to transform, why now, m2, investment, start) are the script to ask, not form fields.
- `manual.routeClient` takes the same answers from the actions bus, sets them in the UI and returns `{ code, then, reason }`, so voice / WebMCP get the suggestion and the person sees what the machine did.
- `manual.createLead` is declared and registered but deliberately fails with "not wired yet: create the lead on the leads page (A-08)" — a declared action that lies about being live would be worse than one that says no.

## Responsive and input check (P-01, P-03)

Verified with Playwright at 360 / 390 / 768 / 1280 / 1920 / 2560 / 3840 (`spec.checkedAt`), light and dark, EN and ES: no horizontal page overflow at any width, no console errors (the only console entry is the dev server's font certificate). Focus order follows the reading order; every control is a library `Button` or `Select` (>= 44 px) with the global focus ring; nothing is hover-only or drag-only. At 2560 / 3840 the `--scale` bands do the work and the reading measure widens (`max-width` 72rem -> 90rem, body text one step up). The widget is two columns from 1024 px (form + sticky result) and one column below it; the result card stops being sticky so a phone never traps the reader.
