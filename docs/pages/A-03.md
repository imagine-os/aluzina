# A-03 - Pipeline

- route: `/#/founder/pipeline`
- surface: founder
- status: built
- spec: `apps/hub/src/modules/founder/specs.ts` (`pipelineSpec`)
- model: Opus 5

## Purpose

The whole commercial-to-delivery flow on one board, on the playbook's fifteen-status architecture (D-033). Leads that have not been contracted yet fill the first four statuses, projects fill the rest, and Alejandra moves anything forward from the card or from its drawer. The board is where the construction gate is felt: a project cannot enter procurement or construction while its design package is not approved.

## Layout (top to bottom)

1. `PageHeader` (A-03) with an "Open leads" primary `Button` (A-08).
2. `FilterBar`: `SearchField` (name, client), type `Select`, approval `Select`, summary "n of m in the pipeline", Clear.
3. `Tabs`: Board / List, each with its count.
4. **Board**: five bands — Lead, Sale, Design, Build, Closed — each a header button with the band's card count and, when expanded, a `Kanban` over that group's statuses. The Closed band starts collapsed. A card is a lead or a project: title, "Lead" or the client name plus the value, a `StatusPill` and ◀ / ▶ buttons that walk the fifteen-status order.
5. **List**: `DataTable` of the same entries — name, kind (`Lead` / `Project` `Badge`), client, service, value, owner, status — sorted by the status order.
6. `Drawer` on activation: the entry's badges, a "Move in the pipeline" section with the ◀ / ▶ buttons **and** the "Move to…" `Select` over all fifteen statuses (blocked ones disabled with a short reason tag) plus the full reason as a note; then the project record (client, type, service, creative direction, approval, lead designer, budget, due date, location, summary) with the legacy phase `Select`, or the read-only lead summary. The footer carries "Mark creative direction as set", "Open in Work" and "Open leads" as they apply.

## Data

Reads `leads` and `projects`. Writes `leads.status`, `projects.pipelineStatus`, `projects.phase` and `projects.creativeDirection`.

## Rules

- **G-06 / G-12** no procurement and no construction before the design package is approved. A project whose `approval` is not `approved` or `client-approved` cannot be moved to `procurement` or `in-construction`: the `Select` option is disabled and tagged `G-06`, the ▶ button is disabled with the full sentence as its title, and the write itself refuses with a toast after re-reading the stored row — so the rule holds however the move is called, including through the actions bus.
- A lead only holds the four lead statuses (`LEAD_STATUS_IDS`); to go further it is converted into a project on A-08.

## Logic

- Board entries are `leads` rows with `projectId === null` plus every `projects` row, so one inquiry is one card from the first message to closure and never appears twice.
- Card ids are `lead:<id>` / `project:<id>`, so the board never confuses the two tables; the actions accept either that id or the bare row id.
- Moves are explicit buttons and a `Select`, never drag (P-03). Each move writes by id with `basedOn` the row the person was looking at (D-024) while the gate is checked against the stored row.
- The "Move to…" `Select` lives in the drawer, not on the card: a `<select>` inside the Kanban's horizontal scroller made the whole document scroll sideways in Chromium, and at 390 px the card has no room for it. The card keeps prev / next.
- The type and approval filters only match projects (a lead has neither), so setting one hides the lead cards; the summary counts what is shown.
- The legacy `projects.phase` vocabulary still drives the Work views (D-033), so the drawer keeps a phase `Select` writing it; `founder.moveProject` still moves the phase and `founder.movePipelineStatus` moves the status. See the decision proposed in `docs/changelog/_pending/crm.md`.
- Bands collapse and expand from their header button (`aria-expanded`), and the state is per visit.

## Actions (P-05)

| id | label | intent | permission | params |
| --- | --- | --- | --- | --- |
| `founder.movePipelineStatus` | Move to a pipeline status | move {project} to the status {status} | `projects.write` | `project: id`, `status: enum` (the 15) |
| `founder.moveProject` | Move project to a phase | move the project {project} to the phase {phase} | `projects.write` | `project: id`, `phase: enum` (the 7) |
| `founder.openProject` | Open project | open the project {project} | `projects.read` | `project: id` |
| `founder.setCreativeDirection` | Set the creative direction | mark the creative direction of {project} as set | `projects.write` | `project: id` |
| `founder.toggleGroup` | Collapse or expand a band | collapse or expand the {group} band of the board | `projects.read` | `group: enum:lead\|sale\|design\|build\|close` |
| `founder.openLeads` | Open leads | open the leads page | `leads.read` | — |

`founder.newLead` is no longer declared here: it lives on A-08, where it creates a real lead.
