# A-09 - Archive review

- route: `/#/founder/archive-review`
- surface: founder (`projects.write`, nav group `projects`, order 12)
- status: built
- spec: `apps/hub/src/modules/founder/specs.ts` (`archiveReviewSpec`)
- model: Opus 5

## Purpose

The archive intake (pass 0019) inferred the type, the status, the client and the year of 186 Dropbox
folders and flagged the ones that look like duplicates (D-060). Changelog 0019 section H listed eleven
things only Alejandra can decide. This page is where she decides them: every archived project is a row
she can correct inline and confirm, one at a time or in bulk, so the answers land in the data instead of
in a chat thread.

## Layout (top to bottom)

1. PageHeader (A-09) with the "Open questions" toggle.
2. Four StatTiles: archived projects, confirmed, pending, flagged (a possible duplicate or an intake note).
3. Collapsible Card "Open questions": the eleven items of changelog 0019 section H, bilingual, each with a button that filters the table to the rows it is about.
4. FilterBar: search, year (with "No year"), type, status, "Pending only" (on by default), "Duplicates only".
5. Bulk row: "Select all shown" + "Confirm selected (n)".
6. DataTable: project (checkbox, cover thumb, name, year · file count, the `confirmado` badge and the Dropbox folder link), inferred type (inline Select), status (inline Select + lifecycle Badge), client (inline Select), year (number Input), intake note (read only), actions (Confirm, "Mark as duplicate of…").
7. Drawer "New client": name, kind (past / current / prospect), sector.

## Data

Reads `projects` (the rows tagged `archive`), `clients`, `relations`. Writes `projects` (`type`,
`pipelineStatus`, `client`, `year`, `tags`, `summary`), creates `clients` rows and `relations` rows
(`for-client`, `replaces`). No schema change.

## Rules

D-060 (inferred facts are marked as inferred), D-024 (every write carries `basedOn`), D-026 (cross-entity
links are `relations`, not ad hoc fields), D-045 (unknowns stay explicit).

## Logic

- The table is `projects` filtered by `tags.includes('archive')`; "Pending only" (default on) hides rows already tagged `confirmado`.
- **Confirm** adds the tag `confirmado` and removes exactly the sentence `Tipo y estado inferidos de la carpeta; confirmar con la fundadora.` from `summary`, keeping the folder line and every note. Confirmation is therefore a tag plus a summary edit: no new column, no new entity.
- The **note** column is every sentence of the summary except the first (the folder line) and that inferred sentence, so it keeps reading correctly after the confirmation edit.
- **Mark as duplicate of…** adds the tag `duplicado`, appends `Duplicado de <name> (<id>).` to the summary and records one `replaces` relation **from the project that is kept to the duplicate**, so "referenced by" on the kept project lists what it supersedes.
- **Client**: picking an existing client writes `projects.client` and links a `for-client` relation once; "New client…" opens the Drawer, creates the `clients` row (the folder name is offered as the name), writes `projects.client` and links the same relation.
- **Year** is written on blur; an empty field writes `null` ("No year").
- Bulk confirmation re-reads each stored row (`data.get`) before writing it, so a row another tab changed is not overwritten from a stale render.
- The eleven open questions are a constant in the page (`OPEN_QUESTIONS`), not a read of the changelog file: a numbered changelog is history and never changes, while this list shrinks as the founder answers.

## Real vs mock / placeholder

Everything on the page writes for real through the DataProvider; there is no Placeholder. The rows are
the seeded archive (`docs/archive/index.json`), so a confirmation lives in the person's local store until
the provider is Supabase.

## Responsive and input check (P-01, P-03)

Verified at 390 and 1280 with Playwright (spec `checkedAt` records 360 / 390 / 768 / 1280 / 1920): no
horizontal page overflow, 0 console errors. Seven columns with three inline editors do not fit in the
960 px content column of a 1280 px screen, so the table keeps a 66 rem minimum and scrolls inside the
DataTable's own scroller; the page never scrolls sideways. Two things were needed for that: the page wraps
the table in `.arev-table` (`overflow-x: clip`), and every `hideLabel` field is `position: relative`,
because the absolutely positioned hidden label would otherwise be laid out against the page and widen it.
Under 768 px the DataTable collapses to stacked cards and the inline editors take the full card width. Every editor is a native `<select>` / `<input>` / checkbox, so
Tab reaches all of them in row order and a d-pad or voice will too; the 44 px target comes from the field
styles. The note column is clamped to four lines at desk widths and shown in full on phones. At 2560 /
3840 the table keeps the shell's max width and the extra space goes to the note and project columns.

## Strings (P-13)

## Open questions

- The eleven items themselves: they stay in the page until Alejandra answers them, and each answer is a row edit here.
- Confirmation is per project, not per field: if she wants to confirm the type but leave the status open, the row has to wait. A per-field confirmation would need a schema change (proposed in the changelog draft, not taken).
- Container folders (question 7) and empty folders (question 8) have no "not a project" action yet: deleting or merging an archived project is not in this pass.
