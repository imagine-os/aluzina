# O-12 - Purchasing control

- route: `/#/ops/purchases`
- surface: ops
- status: built
- spec: `apps/hub/src/modules/ops/specs.ts` (`purchasesSpec`)
- model: Opus 5

## Purpose

Purchasing control of service E (stage 5): one row per purchase, tracked through the six statuses from quotation to installation, with what each project has already committed set against its budget. It is the page that answers "what have we bought, where is it, and how much of the budget is gone".

## Layout (top to bottom)

1. `PageHeader` (O-12) with a "New purchase" primary `Button` (only with `purchases.manage`) and the G-07 rule as a note.
2. Six `StatTile`s, one per `PURCHASE_STATUSES` entry, each with its count and the money in it; activating one filters the table by that status (and activating it again clears the filter).
3. `FilterBar`: search (reference, supplier), project, supplier and status `Select`s, count, Clear.
4. `DataTable`: project, supplier, reference, quantity, price, date, responsible, status `StatusPill`; row action Advance (hidden once installed).
5. One `Card` per project with purchases: committed, project budget, and the share as a toned `Badge`.
6. `Modal` "New purchase": project, supplier, reference, quantity, price, date.
7. `Drawer`: the purchase in full, "Advance to <next status>" and a `Select` that sets any status directly.

## Data

Reads `purchases`, `suppliers`, `projects`. Writes `purchases.status` and creates `purchases` rows.

## Rules

- **G-07** purchases are tracked from quotation to installation (`quoted → approved → paid → ordered → received → installed`, `PURCHASE_STATUSES`).

## Logic

- Advance uses `nextPurchaseStatus()`; it re-reads the stored row first, so a purchase that is already installed answers "already installed" instead of walking backwards from a stale card.
- The `Select` in the drawer sets any status directly, because a real purchase sometimes skips a step (a supplier delivers before the invoice is paid) or goes back one.
- A new purchase always starts at `quoted`, with the person writing it as `responsibleId`.
- **`purchases.priceCop` is the price of the whole purchase, not a unit price** — that is how the seed rows read ("Puestos de trabajo (60)", quantity 60, 84,000,000 COP) — so every total on the page is a plain sum, never price × quantity.
- The share badge is `success` up to 80% of `projects.budgetCop`, `warning` above it and `danger` above 100%; a project with no budget shows an em dash.

## Actions (P-05)

| id | label | intent | permission | params |
| --- | --- | --- | --- | --- |
| `ops.newPurchase` | New purchase | record a purchase of {reference} for {project} | `purchases.manage` | `project: id`, `supplier: id`, `reference: string`, `quantity: number`, `price: number`, `date: date` |
| `ops.advancePurchase` | Advance purchase | advance the purchase {purchase} to the next status | `purchases.manage` | `purchase: id` |
| `ops.setPurchaseStatus` | Set purchase status | set the purchase {purchase} to {status} | `purchases.manage` | `purchase: id`, `status: enum:quoted\|approved\|paid\|ordered\|received\|installed` |
| `ops.filterPurchases` | Filter purchases | show the purchases of {project} from {supplier} with status {status} | `purchases.manage` | `project: id`, `supplier: id`, `status: string` |

All four register while mounted (verified: declared 4, none missing from the live list).

## Components

`PageHeader`, `Button`, `StatTile`, `FilterBar`, `SearchField`, `Select`, `Input`, `DataTable`, `Card`, `Modal`, `Drawer`, `KeyValue`, `StatusPill`, `Badge`.

## Real vs mock / placeholder

Everything is a real write: creating a purchase, advancing it, setting any status. No `Placeholder` on this page. There is no link yet from a selected quote (O-05) to the purchase it becomes — that is a request in the changelog draft. Seed data: the six Noam and Ruta N purchases.

## Responsive and input check (P-01, P-03)

Verified at 360 / 390 / 768 / 1280 / 1920 / 2560 / 3840: no horizontal page scroll, no console errors. The six status tiles wrap into an `auto-fill` grid at 14rem; the table stacks into cards under 768. The status tiles are real `<button>`s (StatTile `onActivate`) so the status filter is reachable by keyboard and touch, not only from the Select.

## Strings (P-13)

Namespace `ops.purchases.*` (plus `ops.common.*`); the status labels come from `PURCHASE_STATUSES` through `pick()`. EN complete, ES complete.
