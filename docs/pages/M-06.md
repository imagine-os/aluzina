# M-06 - Service E: Execution / Construction

- route: `/#/manual/services/execution-construction`
- surface: manual
- status: built
- spec: `apps/hub/src/modules/manual/specs.ts` (`serviceSpec('M-06')`)
- model: Opus 5

## Purpose

Building what was approved: ten stages from the execution proposal to handover and closure, gated by G-12 (no construction without an approved design) and priced on an approved design, never on assumptions (G-13). The page is the delivery manual for service E: what it promises, who it is for, every one of its 10 stages with the full checklist, what the client receives, and where the client goes next. Designers, operations and the founder read the same page; the working checkboxes live on the studio engagement page (`engagements.checks`).

## Layout (top to bottom)

1. `PageHeader`: the service name, the outcome as subtitle, breadcrumb Manual > Execution / Construction, **Print / PDF**.
2. Header card: service code badge, ladder word "Materialization", and a definition list (service promise / operating principle, primary outcome, ladder word, ideal for).
3. Sticky phase index from 1280 px: one `Button` per stage, scrolling its card into view and moving focus to its title.
4. One `Card` per stage (10 of them): numbered title, the read-only checklist of its items (grouped items get a sub-heading), and the playbook's notes.
5. Delivery card: what the client receives.
6. Previous / next service links.

## Data

None through the DataProvider. The whole page is the `SERVICES` entry with `code: 'E'` in `src/domain/playbook.ts`, rendered with `pick(text, lang)`.

## Rules

None enforced on this page; the rules that govern this service are listed on [M-08](M-08.md). G-12 (no construction without an approved design) and G-13 (execution priced on an approved design) shape these stages.

## Logic

- One component (`ManualServicePage`) renders all five services; this route passes `code: 'E'` and its own page code, so each service keeps its own spec, nav entry, page doc and screenshot folder.
- Checklists are read-only: an empty box glyph plus the item text, which prints as a paper checklist and never pretends to be a control that does nothing (P-09).
- The phase index scrolls and focuses rather than linking to `#phase-…`, because the app runs on a HashRouter and an anchor would change the route.
- `manual.jumpToPhase` accepts a phase id (`E-1`) or just its number and does the same from the actions bus.

## Real vs mock / placeholder

Everything is real playbook content, and Print / PDF really prints. No `Placeholder` on this page. Not built: ticking an item here (that is the engagement page), and a per-project view of which items are done.

## Responsive and input check (P-01, P-03)

Verified with Playwright at 360 / 390 / 768 / 1280 / 1920 / 2560 / 3840 (`spec.checkedAt`), light and dark, EN and ES: no horizontal page overflow, no console errors. Every control is a library `Button` (>= 44 px) with the global focus ring; the phase index is a `nav` of buttons, so it works with keyboard, touch, pen and (later) a d-pad; nothing is hover-only or drag-only. The index is hidden below 1280 px (the cards are already in order); the page is long — 10 stage cards + delivery = 11 cards — so print rules keep checklist items and cards from breaking across pages.
