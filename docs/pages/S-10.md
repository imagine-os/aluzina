# S-10 - Service checklist

- route: `/#/studio/checklist`, `/#/studio/checklist/:projectId` (same page, deep-linked)
- surface: studio
- status: built
- spec: `apps/hub/src/modules/studio/specs.ts` (`checklistSpec`)
- model: Opus 5

## Purpose

The per-project tracker over the playbook service a project contracted (D-033). Sarai picks a project, sees which service is being delivered, which phase the engagement is on and how much of it is ticked, then walks the phases one by one: tick each real playbook item, mark the phase complete, advance. For service 03 the page also carries the approval gate that protects construction (G-06 / G-12) and the strategic brief the work was built from.

## Layout (top to bottom)

1. `PageHeader` with the **Brief** button (opens the strategic brief `Drawer`; disabled when the engagement has no brief answers).
2. Project `Select` over the projects that have an engagement, with the hint that only those appear. Choosing one navigates to `/studio/checklist/:projectId`.
3. `Card`: the service name, `project · outcome`, the engagement `StatusPill`, and a `KeyValue` with ladder word, current phase, pipeline status, start date, delivery date and project approval.
4. Three `StatTile`s: current phase (`ticked / total`), whole service (`ticked / total`), position (`n / phases`).
5. One `Card` per phase, as an accordion with the current phase open: number chip, title, a `Current` `Badge` on the current phase, the `n of m items ticked` line, and an Expand / Collapse `Button`. Open: one `Checkbox` per playbook item, the phase notes, and a footer with "Open in …" (where the stage has a page), "Mark phase complete" and, on the current phase, "Advance to next phase".
6. Approval gate `Card` (service 03 only), rendered immediately before stage 19: the rule, the `G-06 / G-12` badge, the project approval and pipeline status, the reason line and "Send to procurement".
7. `Drawer`: the `engagements.brief` answers, read-only.

## Data

Reads `engagements`, `projects` and the playbook (`SERVICES` in `src/domain/playbook.ts` — data, not a table). Writes `engagements.checks`, `engagements.currentPhaseId`, `engagements.status`, `engagements.completedAt` and `projects.pipelineStatus`. Every write carries `{ basedOn: row.updated_at }` (D-024).

## Rules

- **G-06 / G-12** approval gate: construction may begin only after the client approves the final design. "Send to procurement" is enabled only while `projects.approval === 'client-approved'` and the project has not already reached `procurement`; otherwise it is disabled and the card says why.
- **G-09**: closing the last phase of the service writes `status: 'delivered'` and `completedAt`, so every service ends with a formal delivery step.
- The checklist never duplicates the playbook: phases, items and notes come from `SERVICES`, and a tick is `engagements.checks[checkKey(phaseId, index)]`.
- Everything that writes needs `engagements.write`; without it the checkboxes are disabled and the phase / gate buttons are not rendered.

## Logic

- The project comes from the route (`:projectId`) when it is a tracked project, otherwise from the first project in `design-development`, otherwise the first tracked project. Selecting a project navigates, so the view is addressable (P-06) and survives a reload.
- A project can carry more than one engagement (Noam: design delivered, execution running). The open one (`started` / `in-progress`) wins, otherwise the last started. There is no engagement switcher yet — see Open questions.
- "Mark phase complete" ticks every item of that phase in one write; it is disabled when the phase is already complete.
- "Advance to next phase" writes `currentPhaseId` of the next phase and `status: 'in-progress'`; it is disabled on the last phase and only shown on the current phase.
- Stage → page map (service 03): 10 → S-11 `/studio/revisions`, 12 and 13 → S-04 `/studio/materials`, 15 → S-06 `/studio/schedules`, 16 → S-07 `/studio/packs`, 17 → S-05 `/studio/plans`.
- The accordion state resets to "current phase open" whenever the engagement or its current phase changes.

## Actions (P-05)

| id | label | intent | permission | params |
| --- | --- | --- | --- | --- |
| `studio.selectChecklistProject` | Choose project | show the service checklist of {project} | `engagements.read` | `project: id` |
| `studio.togglePhase` | Expand phase | expand or collapse the phase {phase} | `engagements.read` | `phase: string` |
| `studio.tickItem` | Tick checklist item | tick item {item} of phase {phase} | `engagements.write` | `phase: string`, `item: number`, `ok: boolean` |
| `studio.completePhase` | Mark phase complete | mark the phase {phase} complete | `engagements.write` | `phase: string` |
| `studio.advancePhase` | Advance to next phase | advance this engagement to the next phase | `engagements.write` | — |
| `studio.openBrief` | Brief | show the strategic brief of this engagement | `engagements.read` | — |
| `studio.openStagePage` | Open in … | open the page that owns the stage {stage} | `engagements.read` | `stage: string` |
| `studio.sendToProcurement` | Send to procurement | send the approved design of this project to procurement | `engagements.write` | `project: id` |

All eight register while mounted (`useRegisterActions`); the four writing ones skip registration without `engagements.write`. Verified live through `window.__aluzina.actions.run`.

## Real vs mock / placeholder

Everything on this page is real: the checkbox writes, "Mark phase complete", "Advance to next phase" (verified end to end — ticking item 3 of stage 11 on Casa Laureles, completing the stage and advancing moved the engagement to stage 12 "Emotional lighting"), the stage links and "Send to procurement". No `Placeholder` on this page. The gate button is correctly disabled in the demo because no seeded project is `client-approved` yet — that status is written by the client app (C-03).

## Responsive and input check (P-01, P-03)

Verified at 360 / 390 / 768 / 1280 / 1920 / 2560 / 3840, light and dark, EN and ES: no horizontal page overflow at any width, no console or page errors. `checkedAt` records 360 / 390 / 768 / 1280 / 1920. Focus order is project select → service card → tiles → phase cards in playbook order (expand button, then the checkboxes of an open phase, then its footer buttons). The whole checkbox row is the target (>= 44 px); every phase toggle is a real `Button`; nothing is hover-only or drag-only. A long `StatusPill` label (`Design development`) overflowed a three-column `KeyValue` at 768 px, so the service card uses two columns.

## Strings (P-13)

Namespace `studio.checklist.*` plus the shared `studio.col.*` / `studio.nav.*` keys. EN complete, ES complete.

## Open questions

- A project with two engagements (Noam) shows only the open one. Should the page offer an engagement switcher (a second `Select`, one more action id), or is "the service in flight" the right default?
- Should completing the last phase of service 03 also write `projects.pipelineStatus`, or is that only the founder's call through the gate?
- The accordion, the progress line and the checklist body are candidates for `Accordion`, `ProgressBar` and `Checklist` library components (see the changelog draft).
