# D-05 - Plan viewer

- route: `/#/dev/plan`
- surface: dev
- status: built
- spec: `apps/hub/src/modules/tools/specs.ts` (`planSpec`)
- model: Opus 5

## Purpose

The PM viewer the workspace policy asks for on every project: the whole development plan as a board, a list and a dependency timeline, read from `docs/plan/plan.json` (D-037). Justin and any agent can see what is done, what is moving, what is next and what blocks what, with the model named on every task. Tasks are bound by dependencies, not calendar days, so the "timeline" is a dependency order, not a date axis.

## Layout (top to bottom)

1. DesktopShell (dev surface).
2. `PageHeader`: breadcrumb, h1, subtitle with the task count.
3. Note line: plan version, updated date, and the read-only rule (the plan is edited in the repo).
4. Four `StatTile`s: backlog / next / doing / done from the plan; activating one toggles that status filter.
5. `FilterBar`: `SearchField` (id, title, step, model, codes), status `Select`, model `Select`, step `Select`, "x of y" summary, Clear.
6. `Tabs`: Board / List / Timeline.
   - **Board**: a Placeholder "Move a task" button, then `Kanban` with backlog / next / doing / done; each card carries the title, its step, a model `Badge`, one `Badge` per page code and the blocker count.
   - **List**: `DataTable` — id, task, step, status (`StatusPill`), model, codes, depends-on count, changelog; sortable; rows open the drawer.
   - **Timeline**: dependency swimlane, one lane per build-plan step, each task in the column of its dependency depth, SVG arrows between dependencies.
7. `Drawer`: the full task — status, step, model, codes, owner, dependency depth, changelog — plus depends-on, blockers, dependents (each a link that opens that task) and the repo files that carry it.

## Data

None from the DataProvider. `src/plan` (`PLAN`, `planOrder`, `planDepth`, `planBlockers`, `planDependents`, `planTask`) reads `docs/plan/plan.json` through the `@docs` alias.

## Rules

D-037: `docs/plan/plan.json` is the machine-readable plan; `build-plan.md` and `kanban.md` are the human views and must agree with it. The page never writes.

## Logic

- Search matches id, title, step, model and page codes; the three Selects narrow further; the summary counts shown of total.
- The timeline lays tasks out with `planOrder()` inside a lane per step and with `planDepth()` across the columns, so a task can never sit left of anything it depends on. The Timeline organism was not used: it needs real `start` / `end` dates and the plan has none, and inventing dates would put fabricated text next to every bar.
- Dependency arrows are an SVG overlay measured against the bars with a `ResizeObserver`; they are decoration only. Every dependency is also written under its bar as "↳ after …", and the overlay is dropped under 768 px, where the lanes collapse to one column.
- Arrow keys, Home and End move focus between the timeline bars; Enter / Space opens the drawer. Board cards and table rows open the same drawer.
- Moving a card is a `Placeholder` (P-09): `tools.movePlanTask` answers with where the edit belongs instead of changing anything.

## Actions (P-05)

| id | label | intent | permission | params |
| --- | --- | --- | --- | --- |
| `tools.switchPlanView` | Switch plan view | show the plan as a {view} | `dev.tools` | `view: enum:board\|list\|timeline` |
| `tools.searchPlan` | Search the plan | find the plan task {query} | `dev.tools` | `query: string` |
| `tools.filterPlanStatus` | Filter the plan by status | show only {status} tasks | `dev.tools` | `status: enum:all\|done\|doing\|next\|backlog` |
| `tools.filterPlanModel` | Filter the plan by model | show only the tasks of model {model} | `dev.tools` | `model: string` |
| `tools.filterPlanStep` | Filter the plan by step | show only the tasks of step {step} | `dev.tools` | `step: string` |
| `tools.openPlanTask` | Open a plan task | open the plan task {task} | `dev.tools` | `task: id` |
| `tools.movePlanTask` | Move a plan task | move the plan task {task} to {status} | `dev.tools` | `task: id`, `status: enum:done\|doing\|next\|backlog` |

All seven register while the page is mounted and were run through `window.__aluzina.actions.run`.

## Components

`PageHeader`, `StatTile`, `FilterBar`, `SearchField`, `Select`, `Tabs`, `Kanban`, `DataTable`, `StatusPill`, `Badge`, `Drawer`, `KeyValue`, `Button`, `Placeholder`, `EmptyState`. The dependency swimlane is the one piece built from primitives in the page (see "Open questions").

## Real vs mock / placeholder

Real: everything read from `docs/plan/plan.json` (59 tasks in this pass) — counts, filters, board, list, timeline, drawer, blockers and dependents. Placeholder: "Move a task" (the plan is edited in the repo).

## Responsive and input check (P-01, P-03)

Verified at 360, 390, 768, 1280 and 1920 (`spec.checkedAt`), plus a 2560 overflow check: no horizontal page scroll at any width, in light and dark. The Kanban scrolls horizontally inside itself and the timeline stage scrolls inside its frame, never the page. Bars, rows, tabs and buttons are 44 px targets; focus order is header -> tiles -> filters -> tabs -> content -> drawer; the timeline adds arrow / Home / End movement on top of Tab; nothing is hover-only or drag-only (the board has no drag at all).

## Strings (P-13)

Namespace `tools.plan.*` + `core.*`. EN complete, ES complete (Spanish reviewed by the worker, not by the founder).

## Open questions

- The dependency swimlane wants to be a library organism (`DependencyLane`, or a dateless mode on `Timeline`): the QA hub and any future roadmap page will need the same thing.
- Depth is shown as a column position and as text; should the bar also span from column 0 to its depth so the "prerequisite chain" reads as a length?
- 2560 / 3840 were only checked for overflow, not read from ten feet.
